# Карта данных и анализ предметной области

## 1. Описание предметной области
Данная система автоматизирует учёт розничных продаж в сети магазинов. Основные процессы: сканирование товаров на кассе, применение скидок, проведение оплаты и закрытие смены. Пользователи системы: кассиры, администраторы магазинов и аналитики. На основе данных принимаются решения о закупках, анализируется выручка, частые возвраты. Система должна обеспечивать высокую скорость обработки транзакций и надежное хранение чеков.

## 2. Выделение сущностей и атрибутов 

### Описание сущностей:

1. **stores (Магазины):**
    Назначение: Хранение информации о точках продаж.
    Ключевые атрибуты: `store_id` (PK), `address`, `phone`.
    Обоснование типов: `SERIAL` для автоинкремента ID. `TEXT` для адреса (так как длина может быть произвольной). `VARCHAR(20)` для телефона.

2. **`employees` (Сотрудники)**
   * **Назначение:** Учёт кассиров и менеджеров.
   * **Ключевые атрибуты:** `employee_id` (PK), `full_name` (NOT NULL, ПДн), `role` (CHECK: cashier/admin/manager), `store_id` (FK).
   * **Обоснование типов:** `VARCHAR(100)` для ФИО. Ограничение `CHECK` не позволяет создать сотрудника с несуществующей должностью.

3. **`categories` (Категории товаров)**
   * **Назначение:** Справочник категорий (напитки, хлеб и т.д.).
   * **Ключевые атрибуты:** `category_id` (PK), `name` (UNIQUE, NOT NULL).
   * **Обоснование типов:** `UNIQUE` запрещает дублирование названий категорий.

4. **`products` (Товары)**
   * **Назначение:** Каталог товаров с ценами.
   * **Ключевые атрибуты:** `product_id` (PK), `sku` (UNIQUE, артикул), `name` (NOT NULL), `price` (CHECK >= 0, коммерческая тайна), `category_id` (FK).
   * **Обоснование типов:** `NUMERIC(10,2)` выбран для точного хранения денежных сумм без потери копеек (в отличие от FLOAT).

5. **`customers` (Клиенты)**
   * **Назначение:** Программа лояльности (бонусные карты).
   * **Ключевые атрибуты:** `customer_id` (PK), `phone` (UNIQUE, ПДн), `bonus_points` (CHECK >= 0).
   * **Обоснование типов:** `phone` имеет ограничение `UNIQUE`, чтобы один телефон нельзя было привязать к двум разным аккаунтам.

6. **`shifts` (Кассовые смены)**
   * **Назначение:** Учёт рабочего времени кассира и привязка чеков к смене.
   * **Ключевые атрибуты:** `shift_id` (PK), `store_id` (FK), `employee_id` (FK), `open_time`, `close_time`.
   * **Обоснование типов:** `TIMESTAMP` для точного времени. Ограничение `CHECK` гарантирует, что время закрытия смены будет позже времени открытия.

7. **`receipts` (Чеки)**
   * **Назначение:** Заголовок чека (кто, когда, на какую сумму купил).
   * **Ключевые атрибуты:** `receipt_id` (PK), `shift_id` (FK), `customer_id` (FK), `created_at`, `total_amount`.
   * **Обоснование типов:** `BIGSERIAL` используется для ID чека, так как со временем чеков может стать очень много (миллионы), и обычный `SERIAL` (до 2 млрд) может переполниться.

8. **`receipt_items` (Позиции чека)**
   * **Назначение:** Детализация чека (какие именно товары и в каком количестве куплены).
   * **Ключевые атрибуты:** `item_id` (PK), `receipt_id` (FK), `product_id` (FK), `quantity` (CHECK > 0), `price_at_sale`.
   * **Обоснование типов:** `price_at_sale` фиксирует цену на момент продажи, так как цена в каталоге `products` может измениться в будущем (историчность цен).

9. **`payments` (Оплаты)**
   * **Назначение:** Разделение оплаты (наличные, карта). Один чек может быть оплачен двумя способами.
   * **Ключевые атрибуты:** `payment_id` (PK), `receipt_id` (FK), `payment_type` (CHECK: cash/card), `amount` (CHECK > 0).

10. **`returns` (Возвраты)**
    * **Назначение:** Учёт возвратов товаров по чеку.
    * **Ключевые атрибуты:** `return_id` (PK), `receipt_id` (FK), `reason` (причина возврата), `refund_amount`.

### Обоснование связей (FK) и ограничений:
* **Первичные ключи (PK):** Везде используются суррогатные ключи (`SERIAL`), так как они быстрее и надежнее, чем естественные (например, связка ФИО+Дата).
* **Внешние ключи (FK):** Настроено каскадное удаление (`ON DELETE CASCADE`) для позиций чека (`receipt_items`). Если чек отменен и удален, его позиции удаляются автоматически, чтобы не засорять базу.
* **Обязательные поля (NOT NULL):** Критически важные данные (имя товара, цена, сумма чека) не могут быть пустыми.
* **Ссылочная целостность:** Невозможно создать чек (`receipts`), если он не привязан к существующей смене (`shifts`) и кассиру.

## 4. Классификация данных 
В соответствии с законодательством и бизнес-логикой, данные разделены на три категории:
- **Персональные данные:** Номера телефонов клиентов (`customers.phone`), ФИО сотрудников (`employees.full_name`). Требуют ограничения доступа и шифрования при передаче.
- **Коммерческая тайна:** Себестоимость и цены товаров (`products.price`), суммы (`receipts.total_amount`). Доступ имеют только менеджеры и администраторы.
- **Открытые данные:** Адреса магазинов (`stores.address`), названия категорий (`categories.name`), названия товаров (`products.name`).

## 5. Реализация DDL-скрипта
DDL-скрипт, создающий данную структуру с ограничениями (PK, FK, NOT NULL, UNIQUE, CHECK) и B-tree индексами для ускорения поиска (по датам чеков и категориям товаров), реализован в файле `sql/schema.sql`.
